# 小程序端公式渲染：根因分析与方案

> 数据基准：2026-09-02 全量题库 **134 题 / 668 个公式**，实测得出。

---

## 一、现状：降级方案的实际表现

当前小程序用 `utils/latex.js` 把 LaTeX 降级成可读文本。全量扫描结果：

| 分类 | 数量 | 占比 | 表现 |
| --- | --- | --- | --- |
| 简单公式 | 648 | **97.0%** | 可读，与 Web 端观感有差距但能看懂 |
| 复杂公式 | 20 | **3.0%** | 结构失真 |

真正看不了的集中在 **`\begin{array}` 分布列表格**（约 4 题）：

```
源: \begin{array}{c|ccc} X & 0 & a & 1 \\ \hline P & \dfrac13 & \dfrac13 & \dfrac13
现: beginarrayc|ccc X    0    a    1  hline P    (1)/(3)    (1)/(3)    (1)/(3) endarray
```

表格、竖线、`\hline` 全部丢失，只剩一串字符。

而下面这类虽然被判为"复杂"，实际是可读的，属于"不美观但能理解"：

```
\dfrac{\sqrt{2}}{2}   →   (√(2))/(2)
```

**结论**：现状不是"全部不能看"，是"97% 能看、3% 看不了、整体不够美观"。

---

## 二、根因：KaTeX 在 `<rich-text>` 里为什么必死

先说结论：**不是配置问题，是结构不兼容。** 就算把 KaTeX 的 CSS 和字体全塞进小程序，
`<rich-text>` 也渲染不出来。以下四点是实测结果。

### 阻塞点 1：外部样式表不生效，而 KaTeX 是 class 驱动的

实测 `\dfrac{x^{2}}{a^{2}}+\sqrt{2}=1`（一个很普通的公式）：

```
输出长度   3973 字符
class     65 个
内联 style 31 个
```

WeChat 的 `<rich-text>` 跑在隔离渲染环境里，**页面 WXSS 不会层叠进去**，只有节点上的
内联 `style` 属性有效。

KaTeX 的精密排版（分式堆叠、上下标定位、间距微调）几乎全靠 class：
`.katex-base`、`.katex-strut`、`.vlist-t`、`.vlist-t2`、`.pstrut`、`.mfrac`……
这 65 个 class 一失效，输出就退化成一堆裸 `<span>`，彼此重叠挤在一起。

### 阻塞点 2：9 个自定义字体族拿不到

KaTeX 自带排版字体，`katex.min.css` 里有 **20 个 `@font-face`**，覆盖 9 个字体族：

```
KaTeX_Main · KaTeX_Math · KaTeX_AMS · KaTeX_Size1~4 · KaTeX_Script · KaTeX_Typewriter ...
```

字体体积：

| 范围 | 体积 |
| --- | --- |
| 核心子集（Main-Regular / Main-Italic / Math-Italic / Size1-4 / Main-Bold） | 约 102 KB |
| 全部 20 个 woff2 | 1.18 MB |

即便解决了 CSS 层叠，`<rich-text>` 内部节点也拿不到 `wx.loadFontFace` 加载的字体。
缺了 `KaTeX_Size1~4`，大括号、求和号、积分号的伸缩就全错。

### 阻塞点 3：节点白名单（决定性，无法绕过）

KaTeX 为了让根号、花括号能随内容伸缩，会直接输出 **SVG**：

| 公式 | svg | path | math(MathML) |
| --- | --- | --- | --- |
| `\sqrt{2}` | **1** | **1** | 1 |
| `\overbrace{a+b}^{n}` | **3** | **3** | 1 |
| `\xrightarrow{ab}` | **1** | **1** | 1 |
| `\sum_{i=1}^{n}` | 0 | 0 | 1 |

**根号那一横一勾本身就是 SVG 画的。** 而 `<rich-text>` 的节点白名单不含
`svg` / `path` / `math`——这些节点会被直接丢弃。

所以哪怕只渲染一个 `\sqrt{2}`，连根号符号都出不来。
这一点决定了 **KaTeX 输出在 `<rich-text>` 里没有任何可行的补丁路径**。

### 阻塞点 4：体积

| 资源 | 体积 |
| --- | --- |
| katex.min.js | 265.8 KB |
| katex.min.css | 24.1 KB |
| 核心字体 | 约 102 KB（全量 1.18 MB） |

当前小程序主包是 KB 级，装进去会直接跳到 400KB 量级。

## 三、可行方案

要达成"与 Web 端一致"，只有 **A** 和 **B** 两条路——它们都绕开了 `rich-text`。

### 方案 A：mp-html + KaTeX 插件（客户端真渲染）

mp-html 用**真实组件**递归渲染节点，不是 `rich-text`，所以组件 wxss 生效，
KaTeX 的 CSS 和字体才能落地。官方有 katex 插件。

| | |
| --- | --- |
| 还原度 | ★★★★★ 与 Web 端同一套 KaTeX |
| 改动范围 | 仅小程序端，后端不动 |
| 包体代价 | +约 400 KB（JS 266 + CSS 24 + 核心字体 102） |
| 额外工作 | 字体托管到 OSS + `downloadFile` 域名白名单 + `wx.loadFontFace` |
| 风险 | 首字体加载有闪烁；主包变大影响启动速度 |
| 后续成本 | 零，一次接入长期受益 |

### 方案 B：服务端渲染成图片（MathJax → SVG/PNG → OSS）

后端把公式渲染成图片存 OSS，返回 URL，小程序用 `<image>` 显示。

| | |
| --- | --- |
| 还原度 | ★★★★☆ 像素级还原，观感与 Web 端一致 |
| 改动范围 | 新增后端渲染接口 + 小程序改用 `<image>` |
| 包体代价 | **0**，小程序体积不变 |
| 额外工作 | 新增后端依赖（mathjax-full）、OSS 写入、按 LaTeX 哈希去重缓存 |
| 风险 | 公式变图片，无法选中复制；后端多一个较重依赖 |
| 后续成本 | 每题一次渲染（缓存后基本无感），OSS 存储与流量 |

**对你这个项目的特殊优势**：后端和 OSS 都是现成的，不用新建基础设施。

### 方案 C：维持降级 + 只补 3% 的短板

保留现有 97% 的文本降级，只对 `\begin{array}` 这类真正看不了的走服务端图片。

| | |
| --- | --- |
| 还原度 | ★★☆☆☆ 达不到"与 Web 端一致" |
| 改动范围 | 最小 |
| 包体代价 | 0 |
| 后续成本 | 低 |

适合"先把上线跑通，美观后面再说"的节奏。

## 四、决策矩阵

| 维度 | A: mp-html+KaTeX | B: 服务端图片 | C: 维持现状 |
| --- | --- | --- | --- |
| 与 Web 端一致 | 完全一致 | 观感一致 | 差较多 |
| 小程序包体 | +400 KB | 不变 | 不变 |
| 首屏速度 | 略受影响 | 不受影响 | 最快 |
| 后端改动 | 无 | 需新增接口 | 无 |
| 需新增依赖 | mp-html + katex + 字体 | mathjax-full（服务端） | 无 |
| 域名/资质 | 字体需 downloadFile 白名单 | 图片需 downloadFile 白名单 | 无 |
| 可维护性 | 中（依赖第三方组件） | 中（多一个服务） | 高 |
| 实现工作量 | 中 | 中 | 小 |

---

## 五、建议

- **如果你的首要目标是"跟 Web 端一模一样"** → 选 **A**。一次投入，长期零成本，
  公式是真公式（可选中、可缩放、适配深色模式），也是小程序生态的标准做法。
- **如果你更在意小程序轻量和首屏速度**（与你一贯的极简取向一致）→ 选 **B**。
  包体保持 KB 级，后端和 OSS 现成，代价是公式变成图片。
- **如果你想先把上线跑通** → 选 **C**，后续随时可以平滑升级到 A 或 B
  （降级方案与真渲染可以共存，逐题回退）。

三种方案都不需要推翻现有代码：`utils/latex.js` 在 A/B 方案下仍可作为
"图片加载失败时的兜底文本"，不会白写。
